## Восстановление Formula Road API — процедура при падении

Если `api.sverdlik-apps.site` не отвечает или клиенты не грузятся:

```powershell
# 1. Найти PID на порту 3000
netstat -ano | Select-String ":3000"

# 2. Убить зависший процесс (взять PID из п.1)
Stop-Process -Id <PID> -Force

# 3. Перезапустить сервер на VPS через SSH
# PowerShell: ssh -o StrictHostKeyChecking=no root@31.154.67.58 "pm2 restart columbus-api"

# 4. Проверить что API живой
curl https://api.sverdlik-apps.site/health  # ожидаем 404 за <1с (нет endpoint, но отвечает)
```

**Признаки зависания:** LISTENING на 3000 + соединения CLOSE_WAIT + HTTP timeout.  
**cloudflared** (PID проверить: `Get-Process cloudflared`) должен быть запущен отдельно — если упал, тоннель не работает даже при живом сервере.

## Понять до начала — ОБЯЗАТЕЛЬНО, перед каждой задачей

**Никогда не начинать кодить сразу после получения задачи.**

Перед любым изменением кода, файла, конфига или деплоя:

### Шаг 1 — Прояснить задачу (если есть хоть одна неясность)
Задать уточняющие вопросы пока нет полного ответа на три вопроса:
1. **ЧТО** именно нужно сделать (поведение, не реализация)
2. **ГДЕ** именно — какой файл, какая страница, какой endpoint, какой компонент
3. **КОНТЕКСТ** — что сейчас работает рядом и не должно сломаться

Формат уточнения: один конкретный вопрос за раз. Не задавать 5 вопросов сразу.

### Шаг 2 — Диагностика рисков ("Доктор") до начала работы
Перед каждым изменением самостоятельно оценить:
- Какие **другие файлы** зависят от того что я меняю (grep зависимостей)
- Какие **endpoints/маршруты** может сломать изменение сервера
- Какие **страницы** используют общий CSS/JS который я трогаю
- Что произойдёт **при деплое** — есть ли ещё что надо обновить (роут, конфиг, переменная)

Результат озвучить пользователю в 2-3 строки: "Меняю X. Это может повлиять на Y и Z — проверю их тоже."

### Шаг 3 — Только потом писать код

**Почему:** Быстрое "я понял" без понимания приводит к тому что одно фиксируем — другое ломаем. 1 шаг вперёд, 2 назад. Пользователь теряет полдня на исправление того что не просил ломать.

## Дебаггинг — ОБЯЗАТЕЛЬНО через bug-agent

**При любой жалобе на работу системы — немедленно передать bug-agent. CEO и другие агенты не диагностируют баги самостоятельно.**

Триггеры для передачи bug-agent:
- "сломалось", "не работает", "опять", "почему", "что случилось"
- Скриншот с ошибкой, warning banner, пустые данные
- "שגיאת שרת", данные не совпадают с ожидаемыми
- Пользователь недоволен результатом который был ок раньше

Протокол bug-agent (5 шагов):
1. СТОП — не трогать код
2. Собрать данные (PM2 логи, git log, endpoint проверка)
3. Установить timeline — КОГДА сломалось (не что, а когда)
4. Воспроизвести минимальной проверкой
5. Назвать причину с доказательством → предложить фикс → ждать подтверждения

**Никогда не применять фикс до завершения шагов 2-4.**

**Почему:** без воспроизведения агент угадывает. Код меняется, но непонятно — починили баг или просто потрогали рядом. Хороший ремонт начинается с надёжного способа увидеть поломку.

## Честность и верификация — ОБЯЗАТЕЛЬНО

**Никогда не выдавать предположения как факты.**

Правила без исключений:
1. Перед любым утверждением о коде, данных или логике — **сначала прочитать реальный файл** (Read/Grep/Bash). Не угадывать по памяти.
2. Если данные расходятся — читать исходный код, не строить теории.
3. Если точно не знаю — говорить: "не знаю, нужно проверить".
4. Не объяснять расхождения в данных без реальной верификации источника.
5. Не писать "скорее всего", "вероятно", "должно быть" как будто это факт — это не факт.

**Why:** Пользователь многократно (>100 раз) указывал на выдумывание объяснений вместо проверки кода. Это разрушает доверие и приводит к неверным решениям.

**Любая правка HTML/CSS в `docs/*.html`** (шапки, модалки, кнопки, адаптив под планшет/телефон) — перед тем как сказать "готово", проверить визуально через puppeteer (уже стоит как devDependency), не на глаз по коду.

Минимальный процесс:
1. Скрипт в `.scratch/` (за пределы репо не выносить, удалить после проверки) — открыть нужный файл, форсировать нужный экран/состояние через `page.evaluate`, задать viewport под целевое устройство (телефон/планшет)

3. Только потом коммит/деплой

**Why:** словесное описание вёрстки обманчиво — "убрал кнопки в меню" не гарантирует что не осталось переноса строк вразнобой. 2026-08-17 именно так поймали, что шапка всё равно ломалась на ширине планшета, а PNG-иконка на 16px превращалась в кашу пикселей — то и другое увидели только на скриншоте.

## Гигиена сессии — ОБЯЗАТЕЛЬНО

**Проактивно сигнализировать `/clear` или `/compact`**, не дожидаясь пока пользователь упрётся в лимит токенов.

Когда сигнализировать:
1. **Явная смена темы** — сессия перешла с одной несвязанной задачи на другую (например: security-аудит → бизнес-питч → диагностика Cursor). В этот момент предложить `/clear`.
2. **Долгая сессия на одной задаче** — контекст сильно разросся, но задача та же самая (не переключение, а углубление). В этот момент предложить `/compact`.

**Как:** одна короткая фраза в конце ответа, не отдельное сообщение и не навязчиво повторять если пользователь не отреагировал. Сам `/clear`/`/compact` запустить не могу — только предлагать.

**Why:** длинные сессии (8+ часов, >150k контекста) непропорционально дорогие даже с кэшированием — пользователь явно попросил закрепить это письменно 2026-08-11, чтобы не полагаться только на память между сессиями.

## Ponytail — обязательный skill при написании кода

Перед тем как писать или править код в любом файле (JS, PowerShell, SQL, конфиги, скрипты) — **обязательно** применяй дисциплину `.claude/SKILLS/ponytail/SKILL.md`, даже если явно не вызывался через `/ponytail`.

Минимальные правила применения:
1. Перед новым кодом — пройти Ladder of Laziness (нужно ли вообще → есть ли уже в кодовой базе → stdlib → нативная фича → уже установленная зависимость → одна строка → только тогда новый код)
2. Баг-фикс — грепать всех caller'ов функции, чинить в одном месте, не патчить симптом в каждом вызове по отдельности
3. Без незапрошенных абстракций (интерфейс на одну реализацию, конфиг для того что не меняется)
4. Осознанные упрощения — помечать комментарием `// ponytail: <потолок>, апгрейд когда <условие>`
5. По умолчанию уровень **full**; пользователь может явно попросить `lite` или `ultra`

## Priority ERP SQL — обязательный skill

Для любых задач, где есть SQL к Priority ERP, Power BI M коды с источником Priority, поля IVDATE/CURDATE/QUANT, базы `form`/`diller`/`icecrea`/`mmdint` на `192.168.100.246`, **обязательно** загружай и применяй:

- `.claude/SKILLS/priority-sql/SKILL.md`

Минимальные правила применения:
1. Все даты — int (минуты с 01.01.1988), пустая дата = 0 (не NULL)
2. CURDATE фикс: `COALESCE(NULLIF(DOCUMENTS2.CURDATE, 0), [db].dbo.INVOICES.IVDATE)` — применять в SELECT ×3 и GROUP BY ×1
3. QUANT делить на 1000
4. Иврит в SELECT: `NCHAR(8237) + REVERSE(field) + NCHAR(8236)`
