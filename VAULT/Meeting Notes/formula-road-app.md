## Геокодинг — 2026-06-17 ✅

**Задача:** исправить кривую карту из-за неправильного pipeline геокодинга.

**Проблема:** PBI Fabric хранит иврит-адреса в визуальном порядке с LRO-маркерами (U+202D). "הציונות 41" приходило как "‭41 תונויצה" → Google угадывал неправильное место.

**Реализация:**
- `fixBiDiAddress()` — детектирует LRO-маркер, стрипает все BiDi chars, реверсирует Hebrew-сегменты обратно в логический порядок
- Кеш: при загрузке сервера удалены 343 BiDi-испорченных записи; сохранено 1079 чистых
- Порядок геокодеров изменён: Azure → Nominatim → Google (Google угадывает агрессивно — теперь последний)
- `SETTLEMENT_RE`: מושב/קיבוץ/כפר/ישוב без номера дома → пропустить геокодинг, поставить в центр города (`gpsSource='city-center'`)
- **PBI Sibling Lookup**: если другой клиент в PBI с таким же адресом или той же улице ±10 домов имеет GPS → брать его координаты (`gpsSource='pbi-sibling'` / `'pbi-sibling-near'`)
- "⚠ GPS לא מדוייק" — предупреждение в попапе карты для geocoded/pbi-sibling-near клиентов
- `/customers` DAX перестроен: база `'משטח'` (не `'משטח עם כפולות'`), из второй таблицы тянем только `[יום]` и `[סדר ביקור]`; фейковые "קופת מזומן" клиенты исчезли

## Нормализация адресов против гос-справочника МВД — 2026-08-18 ✅

**Задача:** в `לקוחות FORM+I+INT` (FORMULA PBI) один `מספר לקוח` даёт до 3 строк (FORMULA/ICE/INTER), адрес в каждой написан по-разному (опечатки, разный порядок, сокращения). Нужен единый нормализованный адрес на клиента как вход для геокодинга — "один раз и навсегда".

**Источник эталона:** data.gov.il, датасет `israel-streets-synom` (רשות האוכלוסין וההגירה/МВД, 152,130 записей город+улица+синонимы, официальный код улицы, еженедельное обновление). Прямой download-эндпоинт закрыт JS-anti-bot челленджем — качается через чистый CKAN JSON API с пагинацией.

**Реализация** (новые файлы в `scripts/`):
- `fetch-il-streets-registry.js` — скачивает справочник МВД → `il-streets-registry.json` (перекачивать вручную раз в несколько месяцев)
- `normalize-formula-addresses.js` — DAX-выгрузка клиентов (фильтр `שם סוכן`≠"" и `כתובת`≠"") → fuzzy-match город+улица против МВД (exact-first, Levenshtein fallback, порог 0.72) → cross-company sanity-check → Excel + JSON

**Результат на 7510 уникальных клиентах:** confidence high 66.5% / medium 13.7% / low 18.5% / none 1.3%. Между компаниями: agree 3987, conflict всего 68 (1.7% от клиентов с 2+ источниками) — низкий конфликт-рейт подтверждает, что матчинг не гадает случайно; конфликтные строки — реальные расхождения адресов между HEVRA (не баг парсера), кандидат на ручную проверку.

**Побочная находка — реальный баг в проде, НЕ пофикшен:** `fixBiDiAddress` (`server/index.js:1015`) разворачивает буквы только ВНУТРИ каждого ивритского слова, но не разворачивает порядок самих слов — визуально-хранимая PBI-строка требует разворота и того, и другого. Подтверждено на живых данных: `"12 ןרוא זכרמ"` → баг даёт `"12 אורן מרכז"` (бессмысленный порядок) → корректный фикс даёт `"מרכז אורן 12"` (реальное название точки). **Не сделано:** сам геокодинг по нормализованным адресам (следующий шаг — использовать `formula-address-normalized.json` как вход вместо сырых PBI-строк); фикс прод-бага fixBiDiAddress.

**Диагностика fixBiDiAddress завершена, фикс отложен на 2026-08-19:** причина подтверждена (нет `.split(/\s+/).reverse()`, который уже есть в соседней `fixBiDi` :2286), impact измерен на живом LocationIQ (buggy 90% успеха геокодинга vs fixed 97.5%, ~1 из 10-13 многословных адресов проваливался с багом).
