## Геокодинг — 2026-06-17 ✅

**Задача:** исправить кривую карту из-за неправильного pipeline геокодинга.

**Проблема:** PBI Fabric хранит иврит-адреса в визуальном порядке с LRO-маркерами (U+202D). "הציונות 41" приходило как "‭41 תונויצה" → Google угадывал неправильное место.

**Реализация:**
- `fixBiDiAddress()` — детектирует LRO-маркер, стрипает все BiDi chars, реверсирует Hebrew-сегменты обратно в логический порядок
- Кеш: при загрузке сервера удалены 343 BiDi-испорченных записи; сохранено 1079 чистых
- Порядок геокодеров изменён: Azure → Nominatim → Google (Google угадывает агрессивно — теперь последний)
- `SETTLEMENT_RE`: מושב/קיבוץ/כפר/ישוב без номера дома → пропустить геокодинг, поставить в центр города (`gpsSource='city-center'`)
- **PBI Sibling Lookup**: если другой клиент в PBI с таким же адресом или той же улице ±10 домов имеет GPS → брать его координаты (`gpsSource='pbi-sibling'` / `'pbi-sibling-near'`)
- "⚠ GPS לא מדוייק" — предупреждение в попапе карты для geocoded/pbi-sibling-near клиентов
- `/customers` DAX перестроен: база `'משטח'` (не `'משטח עם כפולות'`), из второй таблицы тянем только `[יום]` и `[סדר ביקור]`; фейковые "קופת מזומן" клиенты исчезли

### client-AI модалка — разбивка по семействам + баг с INTER
- Клик по строке "מחלקה" (דגים/גלידה/חלבי) в основной таблице раскрывает настоящие `ALL_PARTS[תאור משפחת מוצר]` под ней — данные уже приходили в DAX, просто не собирались на JS-стороне

- **Реальный DAX-баг, не выдумка**: разбивка INTER по `KARTIS PARIT INTER[פרמטר 2]` первый раз выдала суммы в 100 раз больше тотала клиента (пользователь: "ты там что всю сеть взял??"). Диагностика на реальных данных (custId `1130037`, standalone-скрипт на VPS с тем же `.env`/`powerbi.js`) доказала: НЕ scoping-баг (фильтр по клиенту стоял верно, идентично рабочему `famDax`) — причина в семантике DAX. Мера `[TOTAL SALES (ללא זיכויים מרכזים)]` сама фильтрует `NOT(ALL_PARTS[מק'ט] IN ExcludedProducts)` — явный filter-аргумент CALCULATE на ТОЙ ЖЕ колонке, по которой шла группировка SUMMARIZE, **заменяет** context transition вместо пересечения с ним → каждая SKU-строка получала тотал всего клиента. Фикс: exclusion вынесен наружу CALCULATETABLE, сумма — прямой `SUM`, без обращения к именованной мере (тот же приём уже был в `zikuyDax`/`lastShipDax` в этом файле, просто не был переиспользован сразу)
- Причина найдена через PBIP-экспорт `FORMULA DASHBORD.pbix` → `relationships.tmdl` + `MEASURES TABLE.tmdl` (лежит вне репо: `Desktop/WORKSPACE/FORMULA PBI DOCS/`) — связь `ALL_PARTS↔KARTIS PARIT INTER` оказалась стандартной, дело было не в ней

### Гигиена git — конкурентные сессии в одном рабочем каталоге
**Важное открытие**: в этой сессии параллельно работала вторая сессия Claude Code **в том же самом checkout** (не отдельный worktree). Несколько раз `git add`+`git commit` из одной сессии подхватывал в индексе файлы, застейдженные другой сессией в тот момент — коммит уходил под правильным сообщением, но с чужим (или частично чужим) содержимым, и наоборот. Ничего не потерялось (`git show --stat` после каждого коммита это подтверждал), но пришлось несколько раз разбираться "куда делся мой diff". **Урок на будущее**: если печатаю про "другая сессия уже начала" — это буквально значит второй процесс трогает те же файлы прямо сейчас; после каждого `git commit` обязательно `git show --stat HEAD` чтобы убедиться что содержимое соответствует сообщению, а не слепо доверять успешному коду выхода.
