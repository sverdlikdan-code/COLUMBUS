## Сессия 2026-08-12/13 — client-analytics: от плоской таблицы до gap-анализа по сети

Долгая сессия, `/api/client-analytics/:custId` + `formula-road.html` переписаны почти
полностью поверх фикса из 2026-08-11. Порядок фиксов — по мере поступления фидбека
пользователя вживую по скриншотам.

**Production-баги (не связанные с фичей, всплыли по пути), все задеплоены:**
- Gemini `gemini-2.0-flash-lite` задеприкейтился (2-й раз подряд) → `gemini-flash-lite-latest`
  (alias, чтобы не чинить в 3-й раз).
- BiDi: CSS `direction:auto` — невалидное значение (только `ltr`/`rtl`), браузер игнорил →
  текст с русским+ивритом визуально переставлялся. Фикс: `unicode-bidi:plaintext` +
  явный `dir` по языку.
- Markdown (`**`, `#`) от Gemini рендерился буквально — промпт не запрещал его явно.
- Гонка языков в `_fetchClientAI`: клик по нескольким языкам подряд → медленный ответ
  резолвится позже быстрого и затирает правильный текст. Фикс: проверка
  `_aiState.custId/lang` перед записью в DOM.
- `docs/formula-road.html` дефолт GPS-режима (`aiGpsMode:false, tabletGpsMode:true`) —
  более ранний фикс a34592f6 правил только `territory.html`, эта страница осталась.

**Фича (в порядке наслоения):**
1. Период сравнения: месячная таблица → rolling (тек. 3М vs пред. 3М) → **финально YoY**
   (тек. 3М vs те же 3М год назад) — rolling давал ложный рост/падение на сезонке
   (мороженое летом vs весной).
2. Кашрут-filter: кошерный клиент → `ALL_PARTS[כשרות]="כן"` и в разбивке, и в среднем.
3. Сеть vs частный рынок: `'משטח'[רשתות - פרטי]` = רשתות/שוק פרטי,
   `'משטח'[תאור סוג לקוח]` = имя сети ИЛИ категория (напр. "חנויות", 786 клиентов) —
   **peer-group строится по этому полю в обоих случаях**, просто текст "רשת X" vs
   "קטגוריית X" (споткнулся на грамматике: сопряжённая форма "קטגוריית" не может стоять
   одна без имени — исправлено на "קטגוריה" в standalone-контекстах).
4. Dormant-товары ("сеть/категория продавала 120д, точка не брала 90д") — proxy для
   "байер одобрил товар". Разбито по компании через `מחלקה` (`mish`→ICE_MISH,
   `bdd`→ICE_BDD, `מתוקים  🍬`→INTER, иначе FORMULA) — порядок FORMULA→ICE MISH→
   INTER→ICE BDD. **ICE BDD никогда не даёт деталей по товарам**, только флаг.
5. Company-gap: сеть/категория покупает у компании X, у точки = 0 → это приоритетнее
   любого единичного dormant-товара (структурная дыра, не разовый пропуск).
6. Сток-фильтр FORMULA/ICE_MISH — `'זמינות FORM'/'זמינות ICE'` из **отдельного** PBI
   датасета (`POWERBI_MMD_DATASET_ID`, не тот же что ALL_PARTS). **Баг:** SKU, которого
   вообще нет в таблице наличия (не 0, а отсутствует), трактовался как "есть в наличии"
   — поймано пользователем вживую (SKU 800, חמאה ROSHEN, реально отсутствует в
   `זמינות FORM`). Исправлено: unknown → исключить, не разрешить.
7. Исключена группа "גלידות מותגים" (3 raw-варианта фасовки) из ICE MISH рекомендаций
   целиком, по явной просьбе.
8. Family-deviation: top-7 семейств сети/категории vs доля точки, индекс
   (store%/chain%), + "שאר המשפחות"/"סה"כ 100%" строки (без них проценты молча не
   давали 100%). Порог подсветки 0.7/1.2 (не 1.3 — пользователь поймал живым скриншотом).
9. Фото товаров: `KARTIS PARIT[URL תמונה]` — но у ICE и INTER **свои отдельные** таблицы
   (`KARTIS PARIT ICE`, `KARTIS PARIT INTER`) — основная `KARTIS PARIT` их вообще не
   покрывает (проверено: SKU 503061 отсутствует в основной). Картинки — прямой
   `<img src>` на priority.dilerbmd.com (как в `planogram-editor.html`), без прокси —
   CSP `img-src https:` уже разрешает, а свой прокси не помог бы всё равно
   (X-Session — кастомный заголовок, `<img>` его не передаёт).
10. Тон промпта: убраны категоричные "указывает на/свидетельствует о" → гипотетическая
    формулировка ("возможно...", "стоит проверить"). Добавлен brand-substitution insight
    (слабое+сильное семейство одной категории = возможное замещение бренда) — тоже
    hedged, не как факт.
11. UI: модалка 2x (520→1040px, 80→92vh), шрифты крупнее, `overscroll-behavior:contain`
    на `#ai-modal-body` (единственный скролл-блок в файле без него — вероятная причина
    "не листается" на мобильном; **не проверено визуально на устройстве**, только по коду).

**Важная НЕ-находка:** пользователь заподозрил баг (товар из dormant-листа на самом деле
заказывался 37 дней назад) — перепроверил вживую: код корректен (`storeOrderedDax`
правильно ловит SKU, `Set.has()` правильно исключает). Расхождение со скриншотом —
скорее всего лаг рефреша PBI-датасета (обновляется раз в ~2ч, история `/refreshes`
подтверждена через API) между моментом скриншота и моментом перепроверки, а не ошибка
в логике. Подтверждено: ни один chain/peer-group DAX-запрос не фильтрует по סוכן/AGENT.

**Остаётся:**
- Self-learning контур (обучение на исходе рекомендаций) + голос — отложено пользователем
  явно ("пока думаем"), концептуально обсудили: не полноценное дообучение модели, а
  лёгкий feedback loop (backpressure по факту "сработало/нет" в few-shot).
- Визуальная проверка на реальном мобильном устройстве — не делалась, только CSS-анализ.

## Первоначальный план (до корректировки 2026-08-11) — источники ниже устарели в части SQL

# AI Ассистент "Дилан" — Pre-Visit Brief для продажников

## Концепция

Голосовой/текстовый ассистент для агентов FORMULA. Перед визитом к клиенту агент слышит/читает краткий брифинг по аналитике продаж. Активируется из territory.html при нажатии на клиента.

**Имя:** Дилан (Dylan / דילן)

**Фазы:**
- Фаза 1: Текстовая карточка в territory.html (кнопка "Брифинг" на клиенте)
- Фаза 2: TTS — кнопка "Прочитай" → Web Speech API (браузер, бесплатно)
- Фаза 3: Голосовой триггер "Привет Дилан" → Web Speech Recognition

---

## 6 сигналов брифинга

1. **Динамика продаж** — последние 3 месяца vs тот же период прошлого года. По общей сумме и по семействам
2. **Топ семейств** — рейтинг семейств по продажам за 3М
3. **ICE отдельно** — те же метрики только по базе `icecrea`
4. **Частота заказов** — среднее кол-во документов в месяц
5. **Товары 2+ месяца без заказа** — последний документ по SKU > 60 дней назад. Указать срок на полке (`חיי מדף` из ADIFUT). Если закончились — восстановить присутствие
6. **Отклонение от сети** — если клиент в сети (CTYPE ≠ "חנויות"): сравнить продажи по семействам этого магазина vs среднее по всей сети (группировка через CUSTOMERS.MCUST)

**Кашрут-фильтр:** если клиент кошерный → анализировать только товары с `PARTSPEC.SPEC4 IS NOT NULL`

---

## Архитектура данных (всё подтверждено из PBIP)

### Клиент (CUSTOMERS / CUSTSPEC / CTYPE)

| Поле | SQL |
|---|---|
| Кошерный клиент? | `CUSTSPEC.SPEC10 = 'כן'` |
| Тип сети | `CTYPE.CTYPENAME` (= "חנויות" → частный, иначе сеть) |
| Головной клиент сети | `CUSTOMERS.MCUST → CUSTOMERS.CUSTNAME` |
| Сдрян (менеджер) | `CUSTOMERS.YISS_MANAGER → system.dbo.USERSB.SNAME` |

**Важно:** `CUSTOMERS.PCUST` — всегда 0, не используется. Цепочка строится через `MCUST`.

### Товар (PART / PARTSPEC / FAMILY / ADIFUT)

| Поле | SQL |
|---|---|
| Кошерный товар? | `PARTSPEC.SPEC4 IS NOT NULL AND != ''` |
| Семейство | `FAMILY.FAMILYNAME` + `FAMILY.FAMILYDES` |
| Срок на полке | ADIFUT таблица → поле `חיי MADAF` (дни) |
| Бренд | `PARTSPEC.SPEC7` |

### Продажи (INVOICES + DOCUMENTS)

**Источник в PBI:** `ALL_PARTS` = объединение 6 таблиц:
- `ICE DOCS 23-26` + `ICE INV 23-26` → база `icecrea`
- `INTER DOCS 23-26` + `INTER INV 23-26` → база `diller`  
- `FORM DOCS 23-26` + `FORM INV 23-26` → база `form`

**Ключевые таблицы Priority:**
```
INVOICES          → IVDATE (минуты с 01.01.1988), FINAL, TYPE, DEBIT, CUST, IV
INVOICEITEMS      → QUANT/1000, IVCOST, QPRICE, TOTPERCENT, CREDITFLAG, PART, AGENT
PART              → PARTNAME, PARTDES, FAMILY, COST
FAMILY            → FAMILYNAME, FAMILYDES
CUSTOMERS         → CUST, CUSTNAME (7-значный код), CUSTDES, MCUST
IVTYPES           → TYPE, DEBIT, OTYPE
```

**Фильтры обязательные:**
```sql
INVOICES.FINAL = 'Y'          -- только проведённые
INVOICES.TYPE <> 'R'          -- не возвраты
IVTYPES.OTYPE = 'C'           -- только клиентские документы
WAREHOUSES.WARHSNAME <> '900' -- исключить השמדות (уничтожения)
```

**Формула суммы (₪):**
```sql
CASE WHEN INVOICES.FINAL = 'Y' 
     THEN IVCOST 
     ELSE QPRICE * (100 - TOTPERCENT) / 100 END
* CASE WHEN INVOICES1.DEBIT = 'C' THEN -1 ELSE 1 END  -- кредит-нота
* CASE WHEN INVOICEITEMS.CREDITFLAG = 'Y' THEN 0 ELSE 1 END  -- кредит-строка
```

**Количество:** `QUANT / 1000.0`

**Дата → конвертация:** `DATEADD(MINUTE, IVDATE, '19880101')`

**Исключить клиентов:** 1195002, 1195003 (внутренние)

### Поле "רשתות-שוק פרטי" в ALL_PARTS
```
if [תאור סוג לקוח] = "חנויות" then "שוק פרטי" else "רשתות"
```

## API endpoint план

`GET /api/client-brief/:custId`

Запрашивает все 3 базы параллельно:
1. Продажи 18М (для 3М этот год + 3М прошлый год + частота)
2. Данные клиента (кашрут, сеть, MCUST)
3. Если сеть → продажи всех клиентов с тем же MCUST (для сигнала 6)

Ответ JSON → territory.html рендерит карточку.
