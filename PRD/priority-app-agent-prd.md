# PRD: Priority App Agent — замена Soft Solutions

## Роль
Ведёт полный трек решения "заменить дорогой сторонний модуль заказов Soft Solutions" — от финансового расследования реальной стоимости вендора до практической сборки альтернативы: либо внутри самого Priority ERP (Mobile App Generator, מחولл יישومونים), либо через Formula Road + Priority OData API.

## Цель
Дать руководству Diler B.M.D. обоснованное решение с реальными цифрами (не догадками) и довести выбранный путь до работающего прототипа модуля заказов для ~70 полевых агентов группы (FORMULA+ICE+INTER).

## Проблема
Текущий вендор (Soft Solutions, с 2022 — дочка самой Priority) стоит 147,890₪/год — сумма найдена только после прямой проверки платежей в Priority, не была очевидна заранее. Функционал вендора при этом узкий (3 экрана: фото, срок годности, ввод количества+долг) — Formula Road уже сегодня шире этого для агента и менеджера, не хватает только записи заказа в Priority.

## Два реалистичных пути
1. **Priority Mobile App Generator (מחولл)** — нативный no-code конструктор внутри самого Priority. Не требует отдельного write-API (работает через персональные логины агентов, как уже работает у Soft Solutions), но требует отдельного приложения на телефоне агента (не единый инструмент с Formula Road).
2. **Formula Road + OData API** — единое приложение для агента, но требует платного API-модуля Priority (лицензии + transaction packages), точная цена не подтверждена письменно.

## Задача максимум (уточнено Даном 2026-09-02, определяет приоритет между путями)
Конечная целевая архитектура — **НЕ** заменить Formula Road на מחولл и не дублировать UX. Идеал: сохранить Formula Road как есть (весь текущий функционал — маршруты/карта/клиенты/day-closing/зикуй и т.д.) и добавить в него **ровно один новый экран/кнопку "Заказ"**, который пишет заказ в Priority через OData write-API.

**מחолл — это НЕ целевая архитектура для агентов**, а параллельный исследовательский/резервный путь, который доводится до конца ради двух вещей:
1. Не блокироваться на письменном ответе Priority по цене write-API (пока ответа нет — можно двигаться)
2. Технически проверить сам факт "можно ли программным путём писать заказы в Priority под наш тип лицензии" — даже если в итоге постоянным решением станет не он

При прочих равных, когда сравнение путей будет готово (מחولл-прототип завершён и/или пришёл ответ по цене API), **Formula Road + OData API предпочтительнее** — не требует дублирования UX и переобучения ~70 агентов на два разных приложения. Это приоритет, зафиксированный явно, а не просто один из вариантов.

**Уточнение (Дан, 2026-09-02, тот же день):** это не значит "забросить מחолл ради Formula Road+API". Внутри текущей сборки в מחولл приоритет такой: (1) сначала рабочий флоу заказа end-to-end, (2) потом полировка UX/визуала до уровня Formula Road — если это вообще технически достижимо в מחولл-конструкторе (уже установлено: конструктор не поддерживает кастомный CSS/брендинг — фиксированный нативный UI Priority Mobile, см. находку в памяти проекта 2026-09-02). Заказ важнее полировки, но полировка не отменяется как цель внутри текущего пути.

## Ключевые ограничения
1. **Никаких выдуманных цифр** — реальная стоимость API/write-доступа неизвестна до письменного ответа Priority; в презентациях всегда помечать как открытый вопрос, не факт.
2. **Не автоматизировать браузером боевую Priority-сессию пользователя** — заблокировано защитным механизмом Claude Code как слишком рискованное (2026-09-02). Сборка внутри Priority Web — только пошаговые инструкции пользователю, не прямое действие агента.
3. **Секреты Priority (пароли/токены) — никогда в чат**, только через .env, пользователь вписывает сам.
4. P&L-расчёты из GL Priority (FNCTRANS/TRIALBAL) требуют осторожности — наивный подход даёт нереалистичные числа (проверено, задокументировано в skill).
